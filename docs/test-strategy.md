# Тестова стратегія (Lab 36)

## Критичні сценарії
- Реєстрація пацієнта з перевіркою унікальності медичної картки.
- Призначення лікаря до відділення та блокування повторного призначення.
- Створення запису на прийом з перевіркою часу, конфліктів і статусів.
- Підтвердження/скасування записів і заборонені переходи статусів.
- Повний цикл збереження/завантаження стану (JSON persistence).

## Найскладніші для тестування частини
- Часові залежності (перевірка "майбутнього" часу та статистики): винесено в IClock.
- Файловий I/O та пошкоджений JSON: перевіряється інтеграційно через JsonFileDataStore.
- Комбіновані правила валідації (Composite + Strategy): перевіряються окремо і в складі сервісів.

## Де потрібні mocks, а де реальна інтеграція
- Моки/стаби: IDataStore для імітації IOException та нестабільного I/O.
- Моки/стаби: IClock для детермінованих перевірок часу.
- Реальна інтеграція: JsonFileDataStore + PersistenceService + репозиторії для повного циклу.

## Негативні сценарії, які можуть зламати проєкт
- Дублікати ID у збережених даних.
- Записи з неіснуючими пацієнтами або лікарями.
- Пошкоджений JSON або відсутній файл даних.
- Конфлікти часу (лікар/пацієнт на один слот).
- Повторне підтвердження або повторне скасування запису.
- Порожні колекції та відсутні сутності при операціях.
