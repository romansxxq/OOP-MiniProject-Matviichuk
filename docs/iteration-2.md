# Звіт по Ітерації 2

## Готові use cases
- Реєстрація нового пацієнта.
- Призначення лікаря до конкретного відділення.
- Створення запису на прийом з перевіркою доступності часу.

## Бізнес-правила (зафіксовано у коді та тестах)
- Пацієнт повинен мати валідне ім'я та унікальний номер медичної картки.
- Відділення має коректну назву, поверх не може бути від'ємним.
- Лікаря не можна перепризначити в інше відділення без явної логіки перекидання.
- Запис на прийом можливий лише на майбутній час.
- Лікар не може мати два записи в один і той самий час.
- Пацієнт не може мати два записи в один і той самий час.
- Підтверджувати можна лише нові записи; скасування повторно заборонене.

## Патерн розширення
- Використано Strategy + Composite для валідації записів.
- Додавання нового правила (наприклад, "обмеження по кабінету") можливе через новий клас стратегії без зміни AppointmentService.
- У Lab 37 можна додати нову стратегію, наприклад, перевірку доступності лікаря по календарю.

## Persistence
- Реалізовано JSON-сховище (data/medcore.json) з асинхронним читанням/записом.
- Обробка помилок: відсутній файл, пошкоджений JSON, конфлікти даних (дублікати ID, неіснуючі посилання).
- Стан відновлюється при старті програми, збереження виконується через меню.

## LINQ-запити та аналітика
- Активні записи (без скасованих), відсортовані за часом.
- Розклад конкретного лікаря.
- Пошук пацієнтів за фрагментом імені та/або номером картки.
- Топ лікарів за кількістю записів.
- Агрегована статистика по статусах і майбутніх записах.

## Спеціалізовані колекції
- Dictionary використано в InMemoryRepository для швидкого доступу за ID.
- HashSet застосовано для перевірки унікальності ID при завантаженні даних.

## Зміни у класах та контрактах
- Додано IRepository<T, TId> та IDataStore<T>.
- Розширено AppointmentService (створення/підтвердження/скасування).
- Додано Department, PatientService, DoctorService, DepartmentService, QueryService, PersistenceService.
- Стратегії валідації доповнено CompositeValidationStrategy і новими правилами.

## Найризикованіші сценарії для тестування
- Відновлення стану з пошкодженого JSON та конфліктними даними.
- Конкурентні конфлікти записів (перевірка одночасних слотів).
- Узгодженість ID між сутностями після завантаження.

## Що перевіряти інтеграційними тестами у Lab 36
- Повний цикл: створення даних → збереження → перезапуск → завантаження.
- Бізнес-правила на рівні сервісів (валідація часу, конфліктів, статусів).
- Коректність LINQ-запитів на реальних наборах даних.
- Поведінка при типових I/O помилках.
